## 1. 已定方向（本期就要做）

| 项 | 决定 |
|---|---|
| 图表范围 | **App 本地图 + 网页云端图**，两端各自读各自可信的数据源 |
| 云端历史 | **D1 分层聚合**；KV 继续只存当前状态，心跳仍只写 1 次 KV |
| 分层 | 10 分钟原始 **7 天** / 小时 **35 天** / 日 **5 年（1826 天，约 1830 行）**——`DEFAULT_RETENTION`，想更长只改这个常量 |
| 长周期画法 | 每日 **min/max 区间条** + 每日充电次数；**不做周/月平均电量**（电量是循环量，平均无意义） |
| 充电次数 | **方案 A：云端从采样推断**（已知充电状态下，false/未知 → true 计一次；跨小时/跨日**不重复计**，`charging` 未知的样本既不参与判断也不算「未充电」） |
| 公开档位 | 网页**第一期只开放 24h**；更长档位待隐私评估后再开 |
| 公开接口 | 只读**预生成的导出 JSON**（一次查询 1 行），绝不现场扫描历史表 |
| 反滥用 | 图表**默认不自动加载**，需用户**手动点击**，且需通过 **Cloudflare Turnstile 人机验证** |
| 隐私默认值 | 本地记录 / 云端采集 / 公开显示**三个开关分开，默认全关**；开关必须**服务端生效** |
| App 本地 | 独立 DataStore（7 天、上限约 2048 点）+ Compose Canvas 手绘，**不引 Room、不引图表库** |
| 版本 | v1.2.0，沿用现有正式签名 |

顺带要修的现存问题（不单独排期，跟本期一起做）：

1. `/api/status` 每请求读 2 个 KV key → 约 5 万次请求就能耗尽 KV 读额度。
2. KV 异常被包装成 `200 ok=true` 的「无数据」→ 前端会误显示「从未上报」并清掉旧数据。
3. `SHOW_TEMPERATURE` / `SHOW_NETWORK` / `SHOW_MOOD` 只隐藏界面，**接口照旧返回**字段。

## 2. TODO（本期之后）

### T1 · R2 抗打档【优先级：中，需水晴单独授权】

- 目标：让**图表数据读取完全不进 Worker**，攻击者刷图表不再消耗 Worker 10 万请求/天。
- 做法：Cron 把 5 份预生成 JSON（`status` + 4 档历史）推到 **R2**，用**独立自定义域**直出；该域**不得**被任何 Worker Route 接管。
- 代价与风险：
  - **R2 是计费产品**，超额会产生账单（免费：10 GB 存储 / 100 万 Class A / 1000 万 Class B 每月）→ 需水晴同意后再开。
  - 多一个服务与域名要配，部署步骤变多。
- 若要做，先读 `docs/security-and-quotas.md`（待建）里的边界说明。

### T2 · 公开档位扩展到 7d / 30d / 1y

- 依赖：T1 或先确认「被打时动态接口挂掉可接受」。
- 前置：Turnstile 与手动加载的**误伤率**实测；确认不会拦掉正常访客与手机端。

### T3 · 心情时间线【云端已实现，App 展示待定】

- 云端已落地：`history_mood` 事件表 + 导出里的 `data.mood`，`SHOW_MOOD` 关闭时服务端强制置空。
- 仍未做：App 本地的心情历史展示（本地只存当前值）。
- 隐私敏感度高于电量：默认**不**在公开页展示更多条数，宁可少显示也不要翻旧账。

### T4 · 更长保留层（10 年？）

- **已经按 5 年保留**（日级 1826 行 ≈ 几 MB），所以 3 年 / 5 年历史不需要新架构，改 `DEFAULT_RETENTION.dailyMs` 一个常量即可。
- 若将来要「回看去年某天几点插上充电器」，需新增 **raw/事件长期层**，成本显著上升，另评估。
- 画不下时由前端做**像素级降采样**，不在数据库里先平均。

### T5 · 本地「服务关闭也记录」

- 现状：服务关闭时只记录前台取得的样本，**不保证全天曲线**。
- 全天记录需要独立采集模式（新的保活/唤醒策略），涉及耗电与厂商后台限制，暂不做。

### T6 · 部署自动化（可选）

- 个人站现在是**手动触发部署**（Actions → Run workflow）。若要自动，需重新评估被打风险与回滚流程。

## 3. 踩坑记录（动手前必看）

1. **不要开 `cache.enabled`（Workers Cache）**：官方明确缓存 HIT **仍按标准 Worker 请求计费**，且开启后**原本免费的静态资源请求也会计费**，会毁掉「API 挂了页面还能打开」这个核心优点。
2. **Cache API 只省后端读，不省 Worker 请求**；跨机房、冷缓存仍会回源，不能当全局配额锁。
3. **Cron 不能直接改已部署的 Workers Assets**：运行时的 assets binding 只有 `fetch()`，没有 `put()`。
4. **预生成不能每轮重扫全年**：`144 × 52560 ≈ 756 万行读/天` 会直接超过 D1 免费 500 万行/天，**没人攻击也会自爆**。必须增量聚合。
5. **聚合不能只靠 Cron**：改用「写心跳的**同一事务**（D1 batch）里重算小时/日汇总」，Cron 只负责导出与清理，避免「原始删了还没汇总」的灾难窗口。
6. **汇总必须 `INSERT ... SELECT FROM history_raw` 现算**，不能「读出来算好再写回去」：后者在并发下会用旧快照盖掉新汇总（丢更新）。见 `cloud/src/lib/bucket-sql.ts` 与 `cloud/scripts/d1check.py`（那里按**原文**取 SQL 跑，不复制一份）。
7. **免费版限流是 10 秒窗口 + 10 秒封禁**（不是文档里更早写的「30 次/分钟封 60 秒」），且只有 1 条规则可用；IP 轮换、低速分布式攻击仍能绕过。
8. **Worker 10 万请求/天是最硬的天花板**：约 **1.16 次/秒**持续一天就能耗尽。免费方案只能做到「静态页 + 已发布历史 + 本地数据仍可读」，**不能承诺动态接口永不掉线**。
9. **鉴权失败的请求仍然消耗 Worker 请求**，只是不碰 KV（`heartbeat.ts:21-26` 的顺序是对的，别破坏它）。
10. **「没公开」要在服务端拒绝，不能只是前端不显示**：`HISTORY_RANGES` 里没有的档位要在 `/api/history` 直接 404；同理 `SHOW_*` 关掉后接口返回的字段本身就必须是 `null`。靠前端隐藏 = 开关是假的。
